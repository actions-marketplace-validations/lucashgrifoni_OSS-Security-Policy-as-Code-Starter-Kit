# v8.x migration & adoption guide — applicability engine + ATTESTED

> **Nothing in the current v7.x line changes your results unless you opt in.** The
> ADR-028 applicability engine and the `ATTESTED` state ship **additively, behind
> flags that default to off**. They are released as v7.x minors; the *breaking*
> default flip is reserved for **v8.0.0** and is gated on upstream GA (OpenSSF
> Scorecard v6 / OSPS conformance). This guide explains what the opt-ins do, how to
> adopt them early, and what the eventual v8.0.0 flip will change.

## What shipped (additive, opt-in)

| Capability | Flag | Default | Source |
|---|---|---|---|
| `ATTESTED` is a first-class report state | — (always present in the vocabulary) | n/a | ADR-028 |
| Applicability engine: declared preconditions resolve to `NOT_APPLICABLE` consistently | `evaluate --applicability-engine` | **off** | ADR-028 |
| Emit `ATTESTED` for a verified provenance attestation | `evaluate --enable-attested` | **off** | ADR-028 |

With both flags off (the default), `evaluate` behaves exactly as in v7.0 — same
statuses, same scores, same exit codes. The two flags are independent; enable
either, both, or neither.

## The `ATTESTED` state

`ATTESTED` sits alongside `PASS / FAIL / UNKNOWN / NOT_APPLICABLE` in the
`reports/2.0` vocabulary (see [`reports-contract-v2.0.md`](reports-contract-v2.0.md)).
It means **a control's pass is anchored on a verified attestation**, not merely a
deterministic check.

- It **scores as a pass**, but is reported on its **own** `summary_by_status` line,
  so enabling it never inflates your `PASS` count — a control that becomes
  `ATTESTED` simply moves from `PASS` to `ATTESTED` (total unchanged).
- It is **distinct from `SELF_ATTESTED`** (a maintainer self-claim, e.g. from
  `SECURITY-INSIGHTS.yml`): `ATTESTED` requires a *verified* attestation.
- Consumers that do not care can treat `ATTESTED` as a pass and lose nothing;
  consumers that want the strongest posture can branch on `ATTESTED` specifically.

## `--enable-attested` (verified provenance → ATTESTED)

Today this is wired to **`PROV-VERIFY-061`** (build-provenance verification). The
crypto verification happens **in your CI** — `gh attestation verify` or
`cosign verify-bundle` — and the result is recorded in a structured evidence file:

```text
.oss-policy-kit/evidence/<github|azure|aws>-provenance-artifact.json
```

with a `verification` block (`method`, `verified_at`, `transparency_log_inclusion`,
`issuer`). The kit **validates that record**; it does not itself re-verify the
signature. When the record is fully verified (transparency-log inclusion + a fresh
`verified_at`) and you pass `--enable-attested`, the control resolves to `ATTESTED`
instead of `PASS`.

**Fail-closed:** a missing/false transparency log, a stale or unparseable
`verified_at`, or an absent verification block keeps the prior `FAIL` /
`MANUAL_REVIEW_REQUIRED` outcome — a verification gap is **never** laundered into
`ATTESTED`.

## `--applicability-engine` (declared preconditions → NOT_APPLICABLE)

Controls may declare an inspectable precondition in catalog metadata, e.g.:

```yaml
applicability:
  requires_any_files:
    - "**/Dockerfile"
    - "**/*.Dockerfile"
```

When `--applicability-engine` is set and a control's precondition is unmet, it
resolves to `NOT_APPLICABLE` **consistently** (and is excluded from scoring),
instead of each evaluator deciding ad hoc. The predicate is filesystem-only — no
code execution.

The bundled pilot annotates the container controls (`CONT-IMAGE-001/002/003`),
which already returned `NOT_APPLICABLE` without a Dockerfile — so enabling the
engine today **changes nothing** for the bundled profiles; it only makes the
precondition declared and inspectable. Verify this on your own repos with the
impact script below.

## Measuring impact before you adopt

Run the impact analysis to see exactly which controls (if any) change status when
the opt-ins are enabled, per bundled profile, against a target:

```text
python scripts/v8-applicability-impact.py --target .
```

It evaluates each profile with **both** opt-ins off vs on and prints the
per-control deltas. The two effects are independent:

- **Applicability engine** alone: zero change on a target with no container build
  file (the pilot controls were already `NOT_APPLICABLE`).
- **`--enable-attested`**: where the target ships a verified provenance record,
  `PROV-VERIFY-061` moves from `pass` to `attested` in every profile that includes
  it. That is a pass→pass-grade move (no inflation), and it is exactly the signal
  you are opting into. On the bundled **hardened** example (which ships a verified
  record) this is ~16 profiles; on a repo without that evidence it is zero.

Add `--fail-on-drift` in CI to assert no control moves under the opt-ins.

## What v8.0.0 (the breaking flip) will change

`v8.0.0` will make the applicability engine (and, where evidence supports it,
`ATTESTED`) the **default**, and deprecate the opt-in flags after one cycle. That
flip is **not** scheduled until OpenSSF Scorecard v6 / OSPS conformance reach GA,
so the kit does not freeze its semantics against a moving upstream spec. When it
lands it will ship with a control-impact diff and an explicit migration note. Until
then, the behavior above is strictly opt-in.

## TL;DR

- Do nothing → v7.x behaves like v7.0.
- Want consistent applicability → add `--applicability-engine`.
- Verify provenance in CI and want the strongest state → record the verification
  evidence and add `--enable-attested`.
- Pin nothing breaks today; the breaking default flip is a future, gated v8.0.0.
